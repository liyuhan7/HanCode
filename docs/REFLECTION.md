# 反思报告

> 本报告由学生本人撰写，核心判断与经验来自实际开发过程；初稿完成后使用 AI 辅助润色并核对仓库证据（SPEC_PROCESS.md、AGENT_LOG.md、README.md），特此如实披露。

## 1. 哪些 Superpowers 技能最有用？

最有用的是 `brainstorming`。它用连续追问逼我把"做一个 coding harness"这种模糊想法讲清楚：主贡献到底是反馈闭环深度，还是 workspace-scoped memory？经过几轮对话我修正了最初设想——我不要一个通用 harness，而要一个面向学生课程项目、解决"用 AI 做完作业但过程不沉淀"的方案。这种问答式探讨后来发现市面上也有类似的 skill（如 grillme），说明它的形态确实有效。

其次是"子代理审查"（`requesting-code-review` / `receiving-code-review`）。代码膨胀之后人工逐行审查变得很困难，把审查交给一个新鲜 agent 是很好的实现形式——T16/T17 的独立审查代理确实找出过我漏掉的边界：trace 脱敏可被 cookie、无键名 Bearer token 绕过，checkpoint 的补偿与 manifest 信任边界有缺口，这些靠我本人很难发现。`writing-plans` 让 PLAN 成为可冷启动执行的任务卡，使陌生 agent 能仅凭文档开始 T1/T2，也有价值。

## 2. 哪些部分感觉过于形式化而非实用？

最明显的是 `using-git-worktrees`：我的环境 refs 权限被阻断，worktree 创建失败，只能退回 main 分支，流程在这里变成了负担而非帮助。更重要的是，随模型能力增强，整套 Superpowers 显得越来越"繁重"：太多步骤化约束让 agent 把精力花在流程上，T16/T17 每任务强制多轮新鲜复审代理，到后期收益明显递减，很多是细枝末节的加固。

## 3. TDD 是阻碍还是助力？

对核心机制是放大器，对后期功能是阻碍。在 TraceLogger、CheckpointManager、错误优先级这类"确定性、可审计"的内核机制上，先红后绿的纪律非常有效——先写失败测试逼我明确契约，红阶段真的抓到了问题。但在原型完成后的增量功能开发（TUI、交付管线）中，过重的 TDD 约束会让 agent 把注意力放在"写测试"而不是"实现功能"上，因此我在后期放弃了 TDD 流程，只保留"先验证再宣称完成"的纪律。

## 4. 子智能体驱动开发如何影响自主性和专注力？

任务卡足够清晰时，agent 能长时间自主推进而不脱轨——T16/T17 这类"一个任务卡对应一个机制"的任务，agent 可以独立完成多轮"实现 + 独立审查 + 复审"而不需要我逐行介入；S5 的 R2–R6 一连串任务也验证了在给定明确边界后可以批量推进。但上下文一旦含糊，agent 就会按自己的默认假设走，例如冷启动的第二个 agent 在路径语义、幂等语义上做出了与我的原意不一致的解读。所以专注力主要由任务边界决定，而不是由流程仪式决定。

## 5. 哪种任务粒度效果最佳？

"每步 2–5 分钟"的粒度对我偏小、难以维持。最佳粒度是一个任务卡对应一个明确的机制或模块（如 TraceLogger、CheckpointManager、DeliveryPipeline），边界清楚、可独立验证、可单独回退，agent 不易跑偏。

## 6. SPEC / PLAN 的质量如何影响实现质量？

影响直接而显著，最有说服力的证据是冷启动验证：我换用另一个 agent（OpenCode + GLM-5.2），不提供主开发对话历史，只凭 SPEC + PLAN 启动，结果暴露了 6 处规约缺陷——目录形态不一致（文档在 docs 下但验证目录放在根目录）、缺乏 TDD 红阶段证据、init 会覆盖已有 trace/state 证据文件、task workspace 不依赖 project workspace、`OperationResult.status` 类型边界含糊、Python 版本要求不一致。这些含糊之处正是实现时会偏离的地方，也是单人项目中最接近同侪评审的反馈。规约写清一句，实现就少跑偏一次；反之，一处模糊就会换来一轮返工。

## 7. 哪些提示词 / 上下文策略最有效？

最有效的是"显式边界"：给 agent 明确"只做 X、不做 Y、不改哪些文件、以什么证据为准"，例如"不重写 tooling/test_tools.py、factory.py、delivery_pipeline.py"这类约束。AGENT_LOG 中后期多数任务的成功都靠这种约束，它把 agent 的猜测空间压到最小。其次是 MockLLM——用确定性 action 序列离线验证核心机制，不依赖真实网络，让验证可复现、可审计。再就是给 agent 真实 trace / state 证据而非猜测：交付阶段的 `state_inconsistent` 问题就是靠真实 trace 定位到 AgentLoop blocked 分支复写旧状态的根因。

## 8. 凭据和分发需求迫使我去思考哪些问题？

凭据让我必须认真对待"key 从哪来、存在哪、怎么读"：最终采用 keyring 首选、env / .env 只读的来源优先级，登录与更新用隐藏输入、`status` 只返回来源与掩码而不回显明文，并如实说明 .env 的明文风险。这些约束还传导到 trace 与错误信息——要求不在日志、trace、checkpoint 中打印 secret，并为此做了多轮脱敏加固。分发则逼我回答"全新机器如何跑起来"：最终选 wheel / sdist + `uv tool install`，CI 里建包 + 安装 + 冒烟测试。这两条把"只在本机跑通"变成"可在陌生环境复现"，也让"别人拿到项目后如何安全配置自己的 key"有了明确答案。

## 9. 如果重新开始，我会做出哪些改变？

更早地放弃完整 Superpowers、只保留 TDD 与子代理审查两个核心机制——这是我最终的实际做法，回头看我应该更早下定这个决心；在 brainstorming 阶段就固定文档目录形态，避免冷启动时根目录与 docs 的混乱；任务卡增加"不覆盖已有证据文件"这类显式约束；对后期增量功能减少流程仪式，把省下的精力放在真实验证上，而不是让 agent 反复为流程步骤写形式化记录。

## 10. 对 Superpowers 方法论的评价

它假设"AI 需要一套厚重的流程脚手架来守住纪律"，并假设人类会持续参与评审与决策。前者在大型、模糊、从零开始的 greenfield 任务上成立；但随着模型能力增强、项目进入增量阶段，流程的边际收益快速下降，甚至让 agent 重心偏向测试撰写而非实现。后者恰好是我遇到的最大瓶颈——代码膨胀后人工评审越来越难，而这正是 Superpowers 最依赖的一环。我的结论是：方法论的"纪律内核"（TDD、评审、先验证再完成）价值极高，但它的"形式外壳"（worktree、固定技能序列、每任务多轮复审）应按项目阶段裁剪，而不是无条件全量照搬。
